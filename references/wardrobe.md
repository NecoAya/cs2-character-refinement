# 换装扩展：一个人物，多组选项

本篇与 [阶段执行器](../docs/runner.md) 的配置模板配套；清单分项状态与真实作者产物分别记录。

本扩展定义制作合同和配置接口，运行时切换 adapter 尚待实现。用户可以先预留，以后逐项完善；不能把空模板当成已能换装的成品。用户已有的稳定模型与原始资产保持独立。

## 两种模式与稳定接口

- `reserve`：在新工程中保留网格/材质的逻辑边界，输出 wardrobe.json、资源共享关系、体积测量计划、缺失功能。当前只有一个选项也可登记；不用为未来假想衣服创建空模型或复制贴图。
- `implement`：在同一个 player VMDL 中编译需要发布的变体，完成游戏可用的切换 adapter、初始化/重生恢复、物理与袖套联动、组合验证。每部分单独记录 `reserved / authored / compiled / runtime_verified`，不能一处成功就把整个换装系统标为完成。

复制 `assets/wardrobe.template.json` 为项目 wardrobe.json。选项使用稳定字符串 ID，例如 outfit_uniform、iris_gray；面向用户的名字与编译器的 group 数字索引分离。每次编译后重新提取 ID→实际分组/材质映射，不能把旧编译的索引当永久编号。

配置预留 `slots`、`options`、`defaults`、`rules`、`physics_profiles`、`compiled_bindings`、`runtime_adapter` 和 `size_budget`。模板的空值表示未制作/未测量，不表示可用的“无”选项或零字节。如果提供 none 选项，必须显式登记并验证默认显示。

## 各部位怎么做

| 部位 | 优先实现方式 | 必须一起记录 |
|---|---|---|
| 衣服、耳朵、尾巴，可选头发/眼镜 | 保留独立网格，通过编译后的 mesh/body group 组合控制可见性，使用同一角色骨架 | 根骨、可见组、需要遮挡的身体区域、互斥选项、对应物理配置；衣服还要关联第一人称袖套 |
| 瞳色 | 虹膜保留独立材质槽；同纹理不同颜色在目标 shader/运行时确实支持局部调色时复用纹理 | 材质 ID、共享底纹、可用的局部参数或必要的替代贴图，不用整个角色 tint 代替虹膜颜色 |
| 妆容 | 眼睛和面部材质边界分开；尽量共享基础脸贴图/可用遮罩，小范围变化优先复用 | 原始图层、UV 和遮罩；若 shader 不支持分层，则每款面妆烘焙一次并共享给所有衣服 |

独立“选项槽”是我们的配置设计，不代表所有 CS2 接口都支持任意单槽材质替换。实现时先核对目标 shader、脚本/服务端插件能控制什么。若只能切换整个 material group，枚举需要的妆容+瞳色材质组并复用纹理；不要在 shader 中重复烘焙衣服组合，更不要复制完整人物 VMDL。未支持的调色/切换能力明确标未实现。

## 骨架、物理、遮挡与受击框

- 共用身体和主骨架，所有选项遵守同一 rest frame、缩放和根挂点。不同衣服/尾巴的专属辅助骨只保留确有需要的部分，避免重复整套骨架。
- 每套衣服独立描述覆盖的身体区域和第一人称袖套，不把所有可能穿衣位置的身体永久删除；每个可选组合必须有完整外观。
- 物理配置绑定选项：耳尾/裙子被隐藏不等于模拟自动关闭。核查可用的启停接口；若不能停，测量隐藏链的 CPU 开销并据此减少链长、碰撞器和选项数，不能宣称“隐藏就免费”。
- 切换应先检查组合是否合法，再一次应用所有相关网格、材质、身体遮挡、袖套和物理状态。失败恢复上个有效组合；初始化、重生恢复及服务端/客户端状态一致性都由 runtime adapter 负责验证。
- 身体比例相同的服装变体共用受击框；妆容/耳尾通常不新增伤害区域。若改变身体比例或骨骼绑定则重新验证服务器姿态和伤害。
- 增加 mesh group 可能改变 MDAT 数量和 remap。新换装版必须按真实编译布局适配并验证，不能套用其它项目的固定数量、删 assert 或直接手改骨骼索引。

## 换装也要控制体积

目标是只增加新增选项本身必要的网格/纹理，不复制身体、手、骨架和已共享材质。离线可编辑素材和最终发布包分开：源工程保留选项边界，发布包只包含用户选择发布的选项；优化时不把有意保留的可切换组误删。

1. 同款衣服改色优先复用网格和纹理；共享 shader/材质实例可行时复用，是否有实例/调色接口需核实。不为了每个“衣服×妆容×瞳色×耳尾”生成完整贴图套装。
2. 纹理按实际资源引用去重，相同图片复制为不同文件名并不能保证最终只存一次。合图只在能保持足够像素密度、压缩格式和合理采样/驻留成本时用，不为了少一张图把所有小选项拼成超大图集。
3. 每个选项分别简化，保护脸、手、轮廓、UV 边界和变形区域；各自选择分辨率/压缩格式与 LOD 策略，不把单套参数盲目扩大到整衣柜。
4. 输出三类数字：**当前一套显示时的三角形/draw call/可测运行时开销；所有发布选项的模型+依赖总包；新增一个选项相对已有集合的增量字节**。网格隐藏仍占文件空间，纹理和物理的驻留/计算也需实测或标待测。
5. 用实际资源闭包的集合并集计算总包，单套各自闭包计算对比，新增选项用新旧集合差与真实 VMDL 增量计算。共享资源只计一次，不以衣服数量平均分摊整个 VMDL。
6. `max_package_mib` 等上限留 null，直到用户提供预算或项目实测后定值；缺测量不填 0。达到预算时优先复用、去重复、调整小附件分辨率/细节，再由用户目标确定发布哪些选项。

## 阶段产物与验收

intake 的 wardrobe.json 与预算计划进入快照；appearance 更新源网格/材质映射；rig/firstperson/physics 填绑定和联动；optimization 填单套、全衣柜、每选项增量报告；compile 生成 compiled_bindings；validate 分离离线检查和待用户游戏检查；package 交付配置、必要资源与 runtime adapter。

每阶段把上一阶段清单复制到自己的 `stages/<stage>/wardrobe.json` 再补充，作为该阶段输出一起保存；没有变化也记录继承来源。不要原地修改已完成的 intake 清单，否则会破坏现有执行器的快照哈希。最终 package 的清单是最新版本，其余阶段清单保留作回退与追溯。

检查每个选项至少出现一次、所有默认项、none、被规则禁止的组合、袖套联动、耳尾与发根连接、身体遮挡。测试所有声明支持的妆容/瞳色独立组合，以及更容易穿模的衣服/尾巴组合；组合多时注明具体覆盖了哪些，不声称穷尽。游戏检查增加走动、蹲下、转视角、切武器、换装后物理重置与重生恢复。当前用户负责游戏测试，仍交付明确的切换和 Bot 命令，不自行操作游戏。

## 后续补功能时

保持 schema_version 和已有选项 ID 稳定，增加新项而非随意重排索引；配置升级给出迁移。运行器不实现 wardrobe 游戏控制，不能只填配置就期待切换生效。先为新换装候选建立对应 authoring/编译/运行时 adapter，写清每部分实现状态和检查证据，再在 workflow 的阶段中启用。现有稳定单套包继续保留作回退。
