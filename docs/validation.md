# 验证方法与证据边界

本仓库需要分别验证技能项目、块比较器和具体角色。前两项可以在没有游戏资产的环境中进行；通过它们不能代替第三项。

## 验证仓库与工具

在仓库根目录运行：

```powershell
python -X utf8 -B scripts/validate_project.py
python -X utf8 -B -m unittest discover -s scripts -p "test_*.py" -v
```

发布测试环境是 **Python 3.12.4 / Windows**。上述检查只需要 Python 标准库，不需要启动 CS2、安装技能或下载角色。`-B` 避免生成 Python 字节码缓存。

项目检查用于核对发布文件、技能元数据、内部链接、基础隐私规则、任务模板和 Python 语法。单元测试以合成资源及临时项目构造正常与异常输入，验证解析、比较、阶段协调、快照与命令行行为。具体失败项以脚本输出为准；出现失败时先修复原因，再记录结果。

仓库没有配置 CI、自动安装或自动发布。一次本地检查通过只说明当次检查的文件状态；后续修改涉及的检查仍需重新运行。

## 合成测试能证明什么

测试用例自行生成小型资源头、目录和载荷，不包含真实人物、贴图或游戏二进制。它们适合验证：

- 块相同、改变、新增或删除时的报告行为。
- 同名块不会被单个字典值覆盖，以及允许名单的处理。
- 异常头、目录、越界和重叠载荷等输入的拒绝行为。
- 命令行参数、退出码和输出等已覆盖的接口约定。
- 外部手清单的路径/哈希、阶段证据、检查点、命令失败与输出缺失。
- 完成输出和快照变化、配置变动及不安全输出路径的拒绝行为。

这些样本的结构由测试编写者控制。通过合成测试不能证明所有真实文件都符合这些结构，也不能证明解析出的块内容具有正确的骨架、物理或材质语义。完整覆盖范围应查看 [测试文件](../scripts/test_compare_resource_blocks.py) 及当前测试输出。

协调器测试见 [阶段测试](../scripts/test_workflow.py)。它验证文件和状态合同，不验证 evidence 中陈述的真实性。`record` 要求真实通过的逐项检查，但人工填写 `passed` 本身不构成物理/骨架正确的证明；审阅报告、测量和产物仍是作者责任。

## 通用方法与当前工程的证据

[通用验证示例](../references/evidence-case.md) 说明源检查、编译回读、语义回归、资源预算及运行时观察各自能支持什么结论。示例用于选择检查方法，不提供个人模型履历或任何当前工程的通过证据。

将技能用于角色时，需要取得该工程的真实源、编译资源和当前工具信息，再执行对应验证。仓库合成测试验证工具处理输入和状态的行为，不能证明角色材质、骨架、物理或游戏表现正确。

骨数、节点数、贴图字节数、参数和反馈由当前角色工程维护；没有测量或验收证据时，预算及状态保持未确定。

## 给每项结论标明证据

| 证据层次 | 能支持的结论示例 | 仍需另外检查 |
|---|---|---|
| 源检查 | 目标网格的指定通道为零；某骨使用指定父级 | 导出、编译是否保持该关系 |
| 编译检查 | 编译完成且生成可读产物；日志中告警已分类 | 运行时是否加载这一产物、视觉是否正确 |
| 块比较 | 指定块载荷相同；指定块发生变化 | 变化字段的含义、依赖和实际行为 |
| 离线语义回归 | 所检查骨的绑定基底一致；指定顶点的命名权重保持 | 游戏约束顺序、物理时序及未覆盖姿态 |
| 用户游戏反馈 | 在已知场景和动作中观察到指定表现 | 未测动作、其他候选、性能或唯一根因 |

报告应写出输入身份、检查范围、结果与限制。没有运行文件哈希时仍可记录用户反馈，但不能自行补出实际挂载版本。后来取得的证据追加到记录中，不把历史状态当作永久结论。

## 真实角色的回归步骤

### 1. 固定基线和约定

保存源与成品身份、必要依赖、工具版本及哈希。填写 [任务记录模板](../examples/task-contract.json) 的工程内副本，明确目标、保护项和允许差异。模板只是记录载体，不会自动限制编译器或校验模型。

独立候选与接受版分开保存。采用硬链接时，需要在写入前拆开所有可能被工具改写的文件；编译器重编依赖也可能影响材质和纹理。候选制作后重新核验基线哈希。

### 2. 检查编译和块变化

记录退出码、完整日志、生成文件、时间及哈希。编译成功时也要解释相关告警和权重裁剪等信息。

运行 [资源块比较器](cli.md) 定位变化。要把未允许差异视为命令失败，必须使用 `--enforce`；否则返回 `0` 只说明报告生成成功。允许名单作用于同名块的所有实例，并允许其新增、删除和载荷改变。

`payload_allowlist_passed: true` 不等于模型通过验收。它也不要求文件整体一致；目录顺序、重定位和填充变化有独立限制。资源版本与未解析尾部变化不能通过块名允许名单放行。

### 3. 解释变化的语义

使用当前工程可用的解析器、DCC 或项目检查脚本，继续核对：

- 渲染：位置、法线、切线、UV、材质分配、三角拓扑和命名蒙皮。
- 骨架：骨名与父级、绑定变换、映射、约束、挂点、hitbox 和动画引用。
- 官方动画依赖：必要无蒙皮骨/祖先、约束顺序与整条动作求值；不能仅验证手局部 track。用 [骨架记录模板](../examples/rig-audit.json) 在工程内记录。
- 物理：目标节点、固定或动态分类、初始姿态、碰撞、约束与非目标控制。
- 依赖：真正引用的材质、纹理及外部资源；共享项去重，缺失项明确记录。

上述语义检查并未全部实现于随附比较器。索引或排序变化时按名称与拓扑匹配，不只比较计数；不能为让候选通过而扩大允许名单、忽略不明差异。

### 4. 交付用户观察与恢复

用户在实际游戏环境验收。针对当前问题选择静止、转向、走跑、急停、蹲下、重生或切换等动作，并记录观察范围。本工作流不自行启动或操作游戏，不自动覆盖安装目录。

临时关闭目标飘骨时，说明自然摆动会消失，明确恢复包和覆盖范围。诊断包与恢复包分别标注用途，不能要求用户把两者同时覆盖。完整包与补丁也要写清，补丁列出必需底包。

整体观感接受按实际观察范围记录；没有单项证据时保留碰撞、动作范围、运行身份或性能待确认项。

## 验证记录最低内容

记录候选与基线、时间、输入哈希、工具版本、用户目标、实际改动、保护项结果、编译告警、离线检查范围、游戏反馈范围和恢复方法。归档交付还需检查成员路径、CRC 和逐文件哈希。

源码检查、块比较、依赖检查和实机反馈之间出现矛盾时，先确认输入是否相同，再调查差异。详情见 [验证与交付参考](../references/validation-and-delivery.md)。
