# 常见问题

## 这是自动转模或自动修复工具吗？

2.x 已整合从原始资产到交付的完整技能，附带项目创建、阶段协调、证据记录、恢复和资源比较工具。当前 Codex 使用真实资产和本机工具执行制作，协调器本身不包含任意 FBX 的完整转换器，也不会仅凭症状确定所有骨架和物理参数。

实际修改依赖当前工程、用户允许的范围和可用工具。先了解 [能力与限制](../README.md)，再准备 [当前任务输入](getting-started.md)。

## 必须安装 `cs2-character-workflow` 吗？

不必。2.x 已将完整转模阶段、制作合同、执行协调与精修经验合并到同一个入口。旧技能可以保留，但不需要同时安装。手模和人物素材由用户提供，没有随此次整合分发。

## 手模不对为什么要检查官方骨与约束？

官方动画、武器链和程序约束可能依赖无蒙皮骨，导出或编译裁掉它们会改变实际求值。只看手网格、T-pose 或局部手骨动画，可能漏掉完整驱动链。应逐名核对必要依赖和约束顺序，再比较源与编译蒙皮；同时改动多项时，要做单变量验证才能判断各项影响。不能以数量齐全替代检查，也不能盲目追加重复约束。见 [骨架与约束](../references/rig-and-constraints.md)。

## 创建项目后为什么停在 `needs_authoring`？

这是正在等待作者制作该阶段。Codex 应继续用真实工具完成产物，写检查证据后调用 `record`。运行协调器只负责顺序、快照和状态；完成 JSON 模板不代表模型完成。见 [执行器](runner.md)。

## `WORKFLOW_COMPLETE` 是否表示游戏全部通过？

表示配置中的阶段及指定检查点已按该 run 的合同完成。阶段证据仍须列明范围，游戏视觉、伤害、性能可保持待测。协调器不会验证证据陈述的真实性或模拟游戏，所以不能把这个状态当实机结论。

## 换装、嘴型和每发射击抖动已经实现了吗？

提供制作合同和配置接口，默认状态为预留/未实现。实际控制、同步、重生恢复及专门触发需要项目 adapter 和验证；配置、原生动作响应或静态截图不能代替这些实现。

## 下载或发布仓库后就已经安装了吗？

没有。仓库保存、下载到本地、放入技能发现目录是不同步骤。本仓库未配置自动安装流程，也不代表当前会话已经加载了该技能。具体安装和免安装阅读方式见 [快速开始](getting-started.md)。

## 下载时显示 404 应检查什么？

本仓库可公开下载。先核对仓库地址、分支或标签及具体文件路径，再检查当前网络能否访问 GitHub。不要把访问令牌写进技能文件、截图或带凭据的克隆地址中。

## 需要什么依赖？没装游戏能使用吗？

文档学习和仓库合成测试不需要游戏。随附 Python 工具只用标准库，发布测试环境为 Python 3.12.4 / Windows。

具体角色的读取、编辑和编译可能需要用户自有的 DCC、Workshop Tools 或资源解析器。这些工具没有随仓库提供，角色制作也不能仅靠运行本仓库测试完成。

## 支持所有 Source 2 编译资源吗？

没有这个承诺。块比较器支持已测试的头版本 12 基本目录布局，不同资源即使具有相同头版本，也可能超出其支持范围。遇到不支持的头版本、异常目录或重叠载荷时会拒绝解析。

不要直接改检查条件来强行接受未知格式。先确认文件、工具版本与实际布局，再以可公开的最小合成样本补充支持和测试。

## 比较器返回 `0`，为什么报告还有差异？

默认只生成报告，成功生成时返回 `0`。要使未允许差异导致失败，需要加 `--enforce`。即便用了该参数并通过，也只说明本工具范围内的允许名单检查通过。

允许名单可以放过指定块名的新增、删除和内容改变，不是语义安全证明。完整退出码和字段解释见 [CLI 文档](cli.md)。

## 只改变 RED2，就能说运行效果没变吗？

需要明确结论范围。若当前两个模型的功能块完全一致且只见元数据变化，可以报告这一字节级事实；还需要确认依赖、实际装载文件和检查范围，才能解释本次候选的运行意义。

元数据变化不能作为“头发抽动已经修复”的依据。不要把 `--allow-changed RED2` 当作所有任务的默认名单。

## 头发没有布料权重，为什么还可能抽动？

可见运动还可能来自飘骨、动画、约束、父级或其他间接驱动。仅查某个名称前缀，或只看到源通道为零，不能完整追踪控制关系。

从源导入名单、编译 PHYS、实际命名权重与约束逐层核对，再确认游戏加载的候选。详见 [次级运动](../references/secondary-motion.md)。

## 暂时关闭飘骨后稳定了，是否已经修好？

这可以帮助缩小问题范围，但同时取消了自然摆动。它不能独立证明阻尼、轴向或动态父级是唯一根因。

保留恢复方法，明确该测试的视觉代价；只有用户接受这一设计取舍，才能将临时对照作为正式方案。

## 所有骨骼的 X 轴都必须朝向身体吗？

不能把这句话作为通用规则。局部 +X 沿父子链、指向身体中心、朝角色正前方和 DCC 显示轴是不同目标。先明确向量与坐标系，再检查源与编译数据。

某条导出路线的轴约定不能当作所有 CS2 骨骼的强制要求。计算方法见 [轴向与绑定](../references/axes-and-binding.md)。

## 编译成功、包变小或测试通过，是否说明游戏更流畅？

这些结果分别说明编译、体积或特定检查的状态。FPS、显存、多角色成本和物理稳定性需要相应运行证据。

LOD 的显示面数与全部存储面数也要分开统计；PNG 或 ZIP 大小不能代替实际引用编译纹理的预算。详见 [材质与优化](../references/materials-and-optimization.md)。

## 不同角色可以直接共用骨数和参数吗？

角色的尺度、蒙皮、目标风格、工具版本和预算都可能不同。参数由当前工程的输入、测量和验证决定，不能把另一个工程的配置直接当作推荐值。通用技能提供检查方法和合同模板，不预设个人模型参数。

## 没有视频或截图，是否完全无法诊断？

仍可检查文件身份、源设置、编译输入、材质像素、骨架和依赖。把仍需观感或游戏动作判断的部分标为待测试即可，不必阻塞全部只读排查。

## 如何分享问题而不带出角色和私人信息？

优先提供工具版本、命令结构、已脱敏错误、预期与实际结果，解析器问题尽量用合成样本复现。不要直接提交整个角色目录、原工程或完整日志。

本仓库的协作内容可能公开可见。文件错误可能含本地路径，截图、日志和历史记录也可能包含个人信息；分享前检查实际内容。个人模型工程、参数、履历和反馈不进入公共技能仓库，截图或预览图仅在权利人明确选定后分享。详见 [安全与隐私](../SECURITY.md)。

## 仓库提供哪些可重复的验证？

随附测试自行构造资源头、载荷和临时工程，可以验证工具已覆盖的解析、路径、状态和证据合同行为。[通用验证示例](../references/evidence-case.md) 用来解释检查范围。真实角色验收需要使用者自己的输入和运行环境，记录保存在该角色工程。详见 [验证方法](validation.md)。

## 可以修改仓库或自己的副本吗？

主仓库由所有者维护，协作方式见 [维护规范](../CONTRIBUTING.md)。仓库维护规则不把个人副本一律锁为只读；使用、修改和再分发的许可范围仍见 [来源说明](../SOURCE.md)。目前没有指定开源许可证，不能把公开下载或本地可编辑理解成自动获得未授予的权利。
